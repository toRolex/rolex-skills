# AFK Issue Loop：直接开工的批次交付流水线

## Problem Statement

用户已经通过 `/to-tickets` 将需求拆成可执行的 GitHub Tickets，并建立依赖关系。触发 `/afk-issue-loop` 的目的，是让 agent 立即开始解决这些 Tickets，而不是再次规划任务或先证明整个运行平台可用。

当前 skill 随演进叠加了独立 Planner、无业务能力探测、通用身份握手、双向消息确认、模型升级与无限恢复。正常启动要先消费大量平台协议，才开始读取业务和分派实现。在已观察到的 Pi 会话中，唯一顶层 workflow 只运行了探测子代理，探测成功后整个 workflow 结束，没有进入任何真实 Ticket 的实现。

现有无限恢复还会在同次运行中反复接续失败现场，增加上下文消耗、错误假设和现场残留，令“继续推进”变成复杂的自我修复循环。逐 Ticket 流式合并也增加了调度与交接复杂度，不符合这次优先追求简单、直接、可预测的目标。

用户需要一套能由不同 agent harness 执行的短业务流程：读取已有依赖，成批并行实现和审查，统一合并成功部分，然后继续下一批。失败 Ticket 本次跳过，下次调用再试。

## Solution

采用以下主流程，以 Sandcastle 的 `parallel-planner-with-review` 模板为结构参考，删除其中独立 Planner，并保留本项目必要的依赖与交付验收约束：

**读取依赖 → 一批并行 Implementer→Reviewer → 等本批结束 → 一个 Merger 合并成功部分 → 更新依赖 → 下一批。**

- 控制者直接读取 GitHub 原生依赖并选择就绪 Tickets，不重新拆票或推断业务依赖。
- 首批按可用容量一次派发多个 Implementer；不是先启动一个探测或试运行角色。
- 每个 Ticket 独立从实现进入审查：A 可以审查，B 同时仍在实现。
- 等本批各条管线成功结束或明确失败后，启动一个 Merger，处理本批可验收的成功分支。不是每个 Ticket 各启动一次 Merger，也不要求本批全部成功。
- 本批合并与结果核对结束后，更新真实依赖状态、选择下一批；不在批内为了补位而混入新 Tickets。
- 失败 Ticket 加入本次跳过集合，后续批次不再重试。无关 Tickets 继续；其下游保持依赖阻塞。
- 正常路径使用 harness 已提供的委派与通知功能；必要安全检查放在实际动作发生的位置，不在启动时演练完整故障流程。

## User Stories

1. 作为用户，我想触发 AFK 后直接处理真实 Tickets，以便尽快看到业务进展。
2. 作为用户，我想首批同时启动多个就绪 Ticket 的 Implementer，以便利用并行能力，而不是先跑一个无业务探测。
3. 作为用户，我想执行既有 Ticket 依赖，而不是让另一个 Planner 重新解释它们，以便保持唯一的业务关系来源。
4. 作为用户，我想显式指定待处理的 Ticket 范围，以便控制本次工作目标。
5. 作为用户，我想在未指定编号时继续使用项目既有的就绪 Ticket 选择规则，以便保留熟悉的调用方式。
6. 作为用户，我想清楚区分“需求已准备好”和“前置依赖已完成”，以便未满足依赖的 Ticket 不被误启动。
7. 作为用户，我想原生父 SPEC 只提供业务上下文，以便它不会被误当成需要写代码的 Ticket。
8. 作为用户，我想输入不完整、读取失败或依赖循环时收到具体原因，以便不会把错误误认成无任务可做。
9. 作为用户，我想每批有明确容量上限，以便控制资源消耗和同时占用的现场。
10. 作为用户，我想每个 Ticket 有独立交付现场，以便并行实现互不覆盖。
11. 作为用户，我想单个 Ticket 实现结束后立即进入 Reviewer，以便不必等同批其他实现结束。
12. 作为用户，我想 Reviewer 能核查并直接修正实现、执行必要测试，以便审查形成可交付成果，而不是无休止地往返意见。
13. 作为用户，我想同一现场的实现者退出后再交给审查者，以便不会出现并行写入者。
14. 作为用户，我想整批管线结束后只启动一个 Merger，以便降低合并调用和调度复杂度。
15. 作为用户，我想 Merger 只处理本批经过验收的分支，以便失败实现不会混入主分支。
16. 作为用户，我想同批某个 Ticket 失败时其他 Ticket 仍能完成，以便局部失败不取消全部工作。
17. 作为用户，我想本批全失败或没有可合并成果时跳过 Merger，以便不浪费一次无意义调用。
18. 作为用户，我想 Merger 顺序处理本批分支并核对测试结果，以便目标分支始终只有一个写入者。
19. 作为用户，我想仅关闭实际已交付的 Tickets，以便 Issue 状态反映事实。
20. 作为用户，我想本批结束后刷新依赖再选择下一批，以便刚完成的前置 Ticket 能解锁后续工作。
21. 作为用户，我想未结束批次的后续空位不不断混入新任务，以便批次边界清晰且不会无休止延长。
22. 作为用户，我想失败 Ticket 本次跳过，以便不会在同一个错误现场无限重派。
23. 作为用户，我想正常实现中的测试修正与失败后重启区分开，以便 agent 能正常完成工作，又不会借“仍在修复”无限续跑。
24. 作为用户，我想后续批次记住本次失败集合，以便同一个失败 Ticket 不因仍为 open 而立即被重新选中。
25. 作为用户，我想失败 Ticket 的下游保持等待，同时其他独立 Tickets 继续，以便依赖正确性和局部推进同时成立。
26. 作为用户，我想下一次明确调用重新评估失败 Tickets，以便跳过不会成为永久封禁。
27. 作为用户，我想下一次尝试识别已有提交与残留现场，以便既不盲目续接脏环境，也不丢失有效成果。
28. 作为用户，我想保存简短失败原因和现场位置，以便下次判断有事实依据，不必加载复杂恢复档案。
29. 作为用户，我想未知写入者状态只冻结相关现场，以便不会为了换一个 agent 而重复写入同一分支。
30. 作为用户，我想失败后的停止与观察有明确结束边界，以便不会从启动探测卡住变成退出探测卡住。
31. 作为用户，我想 Merger 部分成功时分别看到已交付和未交付的 Tickets，以便不重复实现已完成成果。
32. 作为用户，我想已验收交付与残留清理分别记录，以便删除现场失败不会被误解为业务代码需要重做。
33. 作为用户，我想主分支出现未解决冲突时暂停后续合并，以便跳过失败不会掩盖被污染的共同现场。
34. 作为用户，我想权限拒绝被原样报告，以便 agent 不会通过换载体或换角色绕过限制。
35. 作为用户，我想相同 skill 在不同 harness 上使用各自已有的对应功能，以便文档不膨胀成供应商 API 对照表。
36. 作为用户，我想只提供最终结果通知的子代理也能执行正常交付流程，以便不被强制中途双向握手阻挡。
37. 作为用户，我想继续使用明确指定的模型，以便任务不会因失败而自行切换模型或供应商。
38. 作为用户，我想详细代码材料和输出留在角色或可寻址记录中，以便控制者上下文主要用于业务调度。
39. 作为用户，我想最终报告区分全部完成、部分失败、依赖阻塞和现场未安全结束，以便不会把任何停止都包装成成功。
40. 作为用户，我想验收能证明首批真正开工、批末正确合并、失败不在本次重试，以便不再用文档检查通过代替执行有效。

## Implementation Decisions

### 1. 业务职责与执行顺序

- 删除独立 Planner 角色。控制者负责读取、筛选和调度已有依赖，不重新设计业务任务。
- 保留 Implementer、Reviewer、Merger 三种交付职责。Implementer 实现；Reviewer 在同 Ticket 现场检查并修正；Merger 顺序合并本批成功分支。
- 批次是本次运行内固定的一组就绪 Tickets。批内各 Ticket 的实现→审查管线并发；同一 Ticket 的阶段串行。
- 本批全部管线结束后才触发批次 Merger。失败是可归类的结果，不要求所有管线成功。
- 下一批只能在上一批合并或无可合并成果的处理结束后建立。本次不采用逐 Ticket 审查后即合并、即补位的流式调度。
- 沿用现有最多四个在途 Ticket 的容量约束，不新增并行配置界面。四是本项目保留的运行约束，不是上游模板的必然要求。
- 单批最多一个 Merger，作用于本批入选分支集合，不为每个分支额外启动一个 Merger。

### 2. 输入与依赖权威

- 保留既有输入方式：显式 Ticket 编号；未指定时读取 open 且具有 `ready-for-agent` 资格的 Tickets。
- GitHub 原生 `blocked-by` 是执行依赖权威。沿用现有初始输入及开放 blocker 闭包的范围规则；所有开放执行节点均须满足执行资格。
- 原生父 SPEC 仅作为上下文，不进入可执行 Ticket 集合。
- 读取过程处理分页、PR 排除、开放依赖闭包、资格、重复与循环关系；不因删除 Planner 而删除输入正确性要求。
- 初始已关闭输入是审计事实，不等于本次执行交付。本次已知的未验收成果不能仅凭 Issue 被关闭就直接认定完成。
- 每批选择前读取或刷新候选 Tickets 的必要资格与依赖。无需重新进行整图的 LLM 规划或重复平台探测。
- 读取失败不能作为空图；关系不完整不能作为无依赖。仅有文本依赖且与所需原生关系不符的输入，应报告具体问题，不自行猜测转换。

### 3. 直接业务启动与 harness 通用性

- 首批直接启动真实 Implementer，携带 Ticket、模板位置、目标现场及必要运行身份。多个就绪 Ticket 在可用容量内一起派发，不等待第一个完成再派其余。
- 删除独立能力探测、仅握手不执行任务的角色、所有载体通用的 IDENTIFY/TASK 往返与强制双向 ACK 协议。
- 启动成功的业务信号是进入真实 Ticket 实现，不是某个探测或握手成功。
- 使用宿主当前暴露的原生任务启动、结果通知、状态和停止功能；操作需要时查询具体接口，不在每次运行前枚举并证明所有未来可能需要的能力。
- 如果宿主要求单一顶层 workflow，该 workflow 包含整条批次循环，不能只包含探测或其他辅助任务后直接返回。
- 保留稳定任务身份、结果关联和重复通知不重复生效的要求，不为此重建跨 harness 消息总线。
- 真实能力缺失或权限拒绝时报告具体阻塞，不自动安装插件、不擅自更换载体或绕过审批。
- 保留用户明确的可用模型选择，删除失败后的自动升级与强制强弱模型配置。

### 4. 失败、本次跳过与再次尝试

- 明确区分本次运行、单 Ticket 尝试与用户下一次调用。上下文压缩或同次会话续接不会清空本次跳过集合。
- Implementer、Reviewer 或合并处理明确失败后，该 Ticket 在本次后续批次中排除，不启动替代角色进行自动重试，不要求用户当场批准恢复。
- 正常尝试内部允许必要的调试、测试和修正；不得把明确失败包装为永不结束的普通工作，继续执行原无限恢复策略。
- 普通工具操作的安全失败处理不等于重新执行整个 Ticket。已产生副作用但结果未知的操作不能盲重发。
- 本次跳过不是完成、关闭或永久放弃。下游不会因 blocker 被跳过而解锁；未启动的下游仍是依赖阻塞，不伪造执行失败。
- 下次用户调用重新获取任务状态并检查相关现场；可利用已有成果，但不得盲续旧进程、自动覆盖改动或以当前 HEAD 掩盖原始实现基线。
- 已验证交付只需处理尚未完成的安全收尾，不因上次清理失败重新派 Implementer。
- 失败记录保持短小：任务、阶段、原因、已有成果、相关现场以及是否存在未确认写入者。取消以完整 runbook 驱动无限重派的职责。

### 5. 批次成功集合与 Merger 验收

- Merger 入选依据是本批实现与审查成果可验收，而不只是子代理正常返回、分支有提交或输出了 COMPLETE。
- 实现失败或审查失败的 Ticket 不回退为“只合实现部分”；没有可交付变化的结果应明确归类，不能仅因工具返回成功就进入合并。
- Reviewer 无新增提交不等于审查失败；已有实现可以在审查、测试和版本证据满足时入选。
- 一批没有入选分支时不启动 Merger，记录结果后从剩余就绪集合选择下一批。
- Merger 在一次调用中顺序处理入选分支，核对冲突处理、测试及实际落入目标分支的结果。
- 批次结果逐 Ticket 登记；汇总信号不代表本批全部成功。Issue 关闭只对应实际已交付成果。
- 部分合并后失败，应核对实际成果，保留已完成交付，未交付部分本次跳过。目标分支存在冲突、未知写入者或未验收修改时，不继续往该现场叠加后续合并。
- 结果与必要证据保存后才能删除相关现场。正常流程不依赖 Merger 中途等待控制者 ACK；具体机械清理归属不强制增加新角色或双向通信框架。
- 合并验收、Issue 关闭事实与现场清理进度分别可辨识。已关闭但未验收、已交付但待清理，都不能丢失相关责任或导致重复实现。

### 6. 安全边界与状态记录

- 状态至少区分待执行、执行中、本次跳过与完成；能表示依赖阻塞、退出未确认和清理未完成的事实。具体字段名、schema 版本及文件拆分不是本 spec 已确认的接口。
- 保留薄的运行记录：足以关联当前运行、批次、Ticket、角色任务、成果及失败情况，不保留旧通用能力绑定与恢复协议的空壳。
- 调度结果与现场占用不能混淆。失败决定本次不再调度，并不证明旧写入者已退出。
- 同一现场只允许一个写入者；角色交接和现场回收依据宿主明确的任务终止语义核实退出。宿主保证覆盖相关写入者终止的最终通知可以作为证据；普通业务完成消息、停止请求受理或 idle 不足为证，不额外强制通用握手或进程探测协议。
- 退出不明时保留现场占用，冻结受影响资源，不启动同现场替代写入者。该 Ticket 可归类为本次失败，但不得把失败归类当成进程已退出。
- 批次屏障等待各管线有明确结果，不因失败项退出未知而无限等待；仅当已知隔离边界能够证明该写入者不影响成功项及目标分支时，才可合并本批独立成功部分。无法确认隔离则有限观察后报告阻塞，不强行推进，也不提前回收占用。
- 失败后的停止与观察有明确有限边界；不能确认安全结束且没有可安全推进工作时，保存事实并返回阻塞报告，而不是永久循环探测。具体期限遵循可用宿主机制，未统一写死数值。
- 旧记录只作为核对依据，不将旧 recovering 状态机械迁移成新任务，也不修改正在运行的旧会话。安全兼容处理只作用于相关现场，不让无关历史记录阻挡所有新工作。

### 7. 文档与现有约定

- 正常启动文档只保留业务主干和动作所需边界。故障细节按需读取；删除重复规则、独立 Planner 模板和不再使用的通用通信协议。
- 保留模板自加载、寻址注入和极简汇报，避免控制者全文重读所有角色材料或输出。
- 各入口介绍、示例、领域词汇、状态校验与容量统计同步更新，避免短主文档仍指向旧重协议；本次不要求测试工作。
- 新批次策略取代此前逐 Ticket 流式合并的草案。原生依赖权威、SPEC 非执行节点、权限和单写者边界继续有效。
- 历史 ADR 保留原决定与原因，明确标注新决定取代的范围，尤其是独立 Planner、无限恢复、旧槽位规则与旧合并边界；不重写历史以伪装过去已经采用新设计。

## Testing Decisions

- 用户明确要求发布，不需要测试。本次重构不要求新增或运行测试，不建立新的测试 seam、测试框架或隔离实跑环境；测试不作为发布或实施的前置门槛。
- 未执行测试就明确报告未测试，不声称已经通过端到端或跨 harness 验证。
- 这项决定针对本次 skill 重构的测试工作，不删除 skill 在实际处理业务 Tickets 时的实现测试、审查及合并验收职责。
- 不自动创建测试 Tickets，不恢复用户现有 Pi 会话，不以发布 spec 为由启动业务实现或合并。

## Out of Scope

- 重新拆票、补写验收条件、从代码或正文重新推断业务依赖。
- 独立 Planner、能力探测工作流、通用握手协议或新的跨 harness 消息框架。
- 本次失败自动重派、无限恢复、失败自动模型升级。
- 逐 Ticket 审查通过后立即合并和即时补位的流式调度。
- 开发新的常驻 agent runtime、后台服务或供应商适配平台。
- 自动安装或升级 Pi 插件、切换供应商、变更用户权限设置。
- 自动清空失败 worktree、重置分支、删除未归属改动或接管用户正在运行的会话。
- 将 spec 自动拆成实施 Tickets，或在 spec 发布后自动开始实现。
- 承诺未经真实验证的全部 harness 兼容性。

## Further Notes
