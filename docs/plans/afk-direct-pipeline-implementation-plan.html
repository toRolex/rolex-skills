01 / 优先审阅的决策

已经确认：允许删除多余协议、合并重复文档；删除 Planner，直接读取原生依赖；失败 Ticket 本次跳过，下次调用再试。以下是落实这些决定所需的推荐方案，并非已经获得确认的实现细节。

D1 · 依赖读取与启动

控制者加载依赖；首批并行派发多个 Implementer

推荐：用小型确定性读取器获取指定 Tickets、开放 blocker 闭包、资格及原生关系，返回可调度快照。读取与结构校验合为一条路径，避免 LLM 建图后再重复整图 live 查询。控制者只消费简短结果，角色自行读取 Issue 正文与代码材料。

理由：/to-tickets 已承担拆票与依赖设计；AFK 只负责执行既定关系。保留分页、循环依赖与输入资格检查，不推断新边、不改票。

取舍：允许一个专用的小脚本，不引入新的常驻调度服务或通用 adapter 框架。初始读取每项关系一次；派发前只局部刷新候选 Ticket 的资格与 blocker 状态，不反复验收整图。出现新增依赖时暂停该候选并更新相关关系。

执行范围建议：沿用现有规则：显式输入及其开放、符合资格的 blocker 都属于可执行集合；派发前展示简短范围摘要，不重新要求逐票确认。如果希望编号范围外的 blocker 仅用于阻塞判断、绝不自动执行，请否决这一点。

输入无法完整读取就明确报告，不能把失败当成“没有工作”。只有正文依赖的旧票不静默当成无依赖，也不凭正文重新推断整个图。

D2 · 流水线与正常启动

三角色交付，四 Ticket 在途，唯一串行合并

推荐：Implementer → Reviewer → Merger；首批把没有未满足依赖的 Tickets 按可用容量一起派发，每 Ticket 一个 Implementer，最多四个在途，不先派一个等待结果后再派其余。之后有空槽立即补位。

合并触发仍待审阅：当前草案为单 Ticket 审查验收后进入串行合并队列；用户指定的上游参照已修正为 parallel-planner-with-review。该模板每 Ticket 的 implement → review 串接，各 Ticket 并发；等本批全部管线 settled 后，筛选正常返回且提交非空的结果，再启动一个 Merger 处理全部入选分支。批次合并还是流式合并尚未决定，本文后续的逐 Ticket 合并与即时补位均为待审草案。

上游筛选边界：Reviewer 可直接修正并提交，并非 approve/reject 审核器。正常返回且有 commit 不等于已验证审查通过；实现、审查或 sandbox close 抛错都会排除该 Ticket。Merger 在一次调用内逐分支合并，关闭实际合入的 Issues；模板不独立验证其返回结果。采纳其结构不代表照搬这些较宽松的验收条件。

使用当前 harness 的原生委派、状态及通知能力。只在调用所需接口时查对应说明，不枚举或演练全部能力。若宿主要求单一顶层 workflow，它承载完整业务循环，而非一个结束即退出的 probe。

理由：保留相对于 Sandcastle 批次等待的优化，又不要求每次调用重新证明平台可用。所有角色任务直接携带业务参数，不先启动“等待 TASK”的空角色。

边界：关键工具实际缺失或拒绝授权时明确停在受影响操作；不擅自安装、不绕过权限、不偷偷更换载体。

D3 · 失败与执行状态

本次跳过与安全退出分开表达

推荐：快照升级为 v2，执行状态为 pending / dispatched / skipped / done；阶段保留 implement / review / merge。增加 slot_held，把执行结果与容量分开；删除 recovering 的本次恢复语义。失败记录只保存 Ticket、阶段、原因、现场、有效成果与退出证据。

失败立即标记 skipped，本次不再调度；旧写入者尚未确认退出时 slot_held=true，确认退出并持久化证据后才释放。pending/done 不占槽，dispatched 占槽，skipped 按退出事实占槽。下游不会因为 blocker 被跳过而解锁；未启动的下游保持 pending，不伪造失败。

等待有界：实际失败后请求停止，使用宿主已有的有限退出等待；无现成边界时默认最多等待 60 秒。到界仍未知则持久化占用，冻结相关现场，不重复停止/探测。其他可推进任务继续；没有可推进工作时结束本次控制循环并报告未确认写入者，不释放其槽，也不宣称其已退出。正常长任务不适用这条失败后的停止期限。

理由：跳过是调度决定，不是进程已经退出。不能用状态精简换来两个写入者。下一次调用重新判断任务资格，历史 skipped 不永久封禁 Ticket。

共同现场失败：若 Merger 在目标分支留下冲突或未知写入者，冻结该合并现场，停止后续合并；安全的独立实现/审查可继续到容量上限。耗尽可推进工作后输出真实阻塞状态，不宣称整批完成。

重试范围：正常实现中的测试修正仍是当前任务的一部分；角色报告失败、异常终止或进入明确失败分支后，本次不再启动替代角色。取消失败后的自动模型升级；保留用户明确指定的可用模型。

D4 · 合并结果与清理所有权

Merger 完成即返回；控制者记录结果后清理现场

推荐：Merger 负责合并、测试、summary 与关闭 Ticket，然后返回精确版本证据并退出，保留 branch/worktree。控制者核实证据、角色与写入子进程退出、目标分支安全可用，再原子登记 done/merged 及待清理事实；随后执行已授权的 Worktrunk 机械清理。

有意调整完成边界：经过核验的交付与现场回收分开。安全的待删除 worktree 不阻塞下游或占用 Ticket 槽；清理失败只记 cleanup_pending，不撤销已验证交付、不重派 Implementer。下次调用核对成果后只处理获授权收尾；若目标分支有冲突或未知写入者，则尚不满足上述完成门，不能解锁下游。

关闭 Issue 但尚未完成控制者验收，不等于本次已交付；再次调用时必须结合旧记录核对，不能仅按 CLOSED 抹掉未完成验收或清理责任。落盘失败时不删除现场。

旧设计中的 ACK：Merger 合并后先发消息询问控制者“结果是否已经保存，可以删 worktree 吗”，收到确认后才清理并结束。新建议取消这段中途对话：Merger 返回结果并结束，控制者保存结果后自行清理。这与等待其他 Ticket 完成无关。

理由：通过职责顺序消除“Merger 等确认、控制者等完成”的双向通信依赖。只提供最终结果通知的子代理也能完成正常流程。控制者不接手代码实现、冲突修复或业务测试修正。

代价：控制者新增明确、窄范围的机械收尾职责。若此职责边界不接受，则必须保留额外的清理委派；不推荐恢复通用消息总线。

D5 · 下次调用与旧记录

重新选择任务，不自动复活旧阶段

推荐：保留一个版本化的薄运行快照及失败记录，不构建通用恢复引擎。下次调用重读 Issue 与依赖，并核对相关 branch/worktree 的已有成果和旧写入者。历史记录只帮助判断，不自动跳过审查或授权写入。

同次运行的上下文续接沿用 run_id，不能借续接重试 skipped；用户下一次 AFK 调用才建立新 run_id。旧版 v1 的 recovering、模型升级、peer 握手与 dispatch 记录只读核对并保留，不原地机械迁移为可执行 v2 状态。

相关现场有未确认写入者时保留并报告；安全的失败现场保留给下一次明确尝试，不强制清空、重置或删除用户改动。未完成 merge、已关闭但未验收以及待清理现场分别核对，不把所有残留都重新交给 Implementer。保留原始基线，不以当前 HEAD 掩盖已有修改。

理由：避免“重新调用”变成原恢复引擎的别名，也避免静默迁移把残留状态误当成干净起点。未涉及的旧记录不阻止独立 Ticket 开工。

审阅方式：请对 D1–D5 分别确认或指出异议；例如“D1、D2、D3、D5 同意；D4 不让控制者清理”。未审阅前不开始重构。被否决的决策先更新本计划。

02 / 目标执行流程

用户触发
  → 读取真实 Issues / 原生依赖 / 必要现场信息
  → 选择就绪 Ticket，直接派 Implementer（最多四个在途）
  → 单 Ticket 实现完成 → Reviewer
  → 审查通过 → 唯一串行 Merger
  → 结果返回 → 验收、退出与安全目标核验 → 落盘 done → 补位
  → 已授权现场回收（失败单独记录，不撤销已验证交付）

任一交付阶段失败（不含已交付后的机械回收）
  → skipped，记录原因与现场；退出未知仍占槽
  → 确认旧写入者退出 → 持久化证据 / 释放槽
  → 其他独立 Ticket 继续；下游等待

无可推进工作
  → 区分全部完成、部分跳过、依赖阻塞、等待安全退出
  → 给出简短结果，不轮询一个注定不能推进的循环

四槽是 Ticket 容量，不是四个同时运行的角色。失败现场尚未安全结束时不释放容量。正常路径不读故障恢复手册；只读 Issue/依赖不是“无意义探测”，完整平台自检才是要删除的前置负担。

03 / 验收：先验证能开工，再谈文档完整

场景通过标准验证层
无旧现场、A/B 独立就绪首批直接启动 A/B 的 Implementer，不等 A 完成才启动 B；四个以上就绪时按四槽上限补满。无 Planner、probe-only workflow、IDENTIFY/TASK 往返执行 trace；静态检查只能辅助
A 阻塞 B，C 独立A/C 可启动；A 完整交付前 B 不启动；A 失败本次只跳过 A，B 等待，C 继续确定性依赖与状态测试 + 运行 trace
四个在途，其中一个失败本次不重派；退出未知时不出现第五个 Ticket；退出确认后允许安全补位槽计数与调度场景测试
审查先后完成先通过的 Ticket 即进入串行合并，不等待全部 Implementer/Reviewer事件顺序 trace
子代理只有最终结果Merger 可正常返回；结果落盘前不清理；没有等 ACK 的死锁集成场景与现场证据
下次调用重遇 skipped / 旧 recovering可重新评估任务，但不盲复活旧写入者、不覆盖脏现场、不自动信任旧审查结果旧记录 fixture 与现场测试
接口错误、依赖环、权限拒绝原因明确；不当成空列表、完成或无依赖，不通过换载体绕过脚本错误路径测试
快照后新增 blocker候选派发前的局部刷新发现阻塞，不依赖旧快照强行派发GitHub 响应序列 fixture
失败后永远无法确认退出在有限等待后保留占用并报告；没有可推进工作时返回，不无限探测故障注入 + trace
合并验收成功、清理失败、再次调用不撤销 done、不重做实现；保留 cleanup_pending，核实后仅做获授权收尾清理动作 stub + 独立现场

必须分开报告：脚本测试、静态文档检查、真实 harness 冒烟。原有 73 个脚本测试不证明模型能从入口推进到业务。历史 Pi 日志可作为反例，不伪装为修复后的执行重放。

真实验证边界：在经授权的独立测试仓库与测试 Tickets 中验证，不恢复用户当前 Pi 会话、不使用其生产 Issue 做自动实验。若没有可运行环境，明确标为未验证，不宣布跨 harness 已通过。

04 / 实施顺序与机械性整理

  1. 冻结基线。保存本次任务的变更边界，保留现有未提交改动；新建独立 implementation notes。锁定根因反例与状态场景，不把全文关键字断言当作行为回归测试。
  2. 依赖与状态先落地。实现单次读取的依赖快照路径，调整状态校验与槽计数；为 skipped、等待退出、旧记录及错误响应编写测试，再替换 Planner 入口。
  3. 改短主流程。重写 SKILL 正常路径，直接业务分派；同步三角色职责和模板，去掉 probe、所有角色通用身份握手、双向 durable ack 与失败自动升级。
  4. 按需披露异常。将失败记录、相关现场判断和手动再次调用的说明收敛到一处；保留最小权限与单写者边界，不保留原无限恢复引擎的空壳。
  5. 整理引用。删除不再使用的 Planner 模板与通信协议文件前检查内容与全部引用；合并 REFERENCE、现场绑定和示例的重复规则。同步 router、README、领域词汇与相关脚本注释；不新增另一份供应商接口对照。
  6. 处理历史约定。保留旧 ADR 的历史事实，对与新失败策略冲突的决定注明被新决定取代；在实际状态/兼容性取舍确需长期解释时写一份精简 ADR，不为每处删文档建立 ADR。
  7. 验收与审阅。运行脚本测试、格式和链接检查，再执行获授权的真实行为验证；分别报告结果与未覆盖项。没有明确请求不提交或推送。

  • 当前领域词汇表已确认三角色、就绪 Ticket、本次跳过与再次尝试。
  • Git 历史：9351dbd 业务扫描后分派；41e2408 引入四角色；fdd94f8 引入流式合并；当前未提交的通用能力门扩大了正常启动负担。

  • Sandcastle parallel-planner-with-review是用户指定参照：每 Ticket 实现→审查，各管线并发，allSettled 后单 Merger 合并本批入选分支。合并触发方案仍待确认；不再用无 Reviewer 的 parallel-planner 模板推论。

非目标：重写 to-tickets 的拆票策略、开发新的 agent runtime、自动安装 Pi 插件、迁移用户正在运行的会话、删除残留业务现场、承诺未经实测的所有 harness 兼容性。
