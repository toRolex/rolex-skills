为什么需要它

/afk-issue-loop 在独立 daemon 里批量调度 Implementer、Reviewer 和共享 Merger。 发起 skill 的会话握手后就可以退出，但真正的工作还在后台 CLI 里继续。

问题是：用户看不到它在干什么。过去只能靠 run 级 status、结构化事件文件和每个 Role 的原始日志拼凑。这些信息还有容易误判的层次——

  • 进程活着 ≠ Agent 在有效工作
  • tool-call 被观察到 ≠ 工具已完成
  • Role 自报 passed ≠ Gate 接受（截图里 #9 就是活例子）
  • Role 退出 ≠ Ticket 已交付
  • 共享 Merger ≠ 每个 Ticket 各有一个 Merger

所以目标不是「再做一个日志查看器」，而是让这层层区别在界面上无法被混淆。

四条事实线，永不互相冒充

PROCESS

进程

planned → running → ended。只说明进程状态，不说明工作有效。

SELF-REPORT

角色自报

Agent 输出封套里的 passed/failed/blocked。是声明，不是结论。

GATE

引擎裁决

engine 独立核实 Self-report、测试与 Git deliverable 后的接受或拒绝。

DELIVERY

交付

逐票 merge / summary / close 结果，独立于上面三层。

关键约束：Gate 与 Delivery 必须由 engine 显式发布，界面不得从 Self-report、role-end 或 Merger 汇总反推。 这条直接决定了下面的数据模型。

六个设计决定

1 · Observation journal 与核心事件分离

现有 events.jsonl 承担调度与恢复正确性，写失败会让 run 失败——这是有意的语义，不能降级。 所以另建一份 best-effort 的 Observation journal：写失败只把状态标成 degraded/incomplete， run 照常继续，绝不抛进核心失败路径。

2 · 原始 payload 在解析前入库

provider parser 的职责是过滤与业务判定，会丢掉未知事件和大量字段。Dashboard 要的是完整原文， 所以 raw line 在 parseLine() 之前就写入 journal；typed 事件（text-delta、tool-call）只是附加视图。

3 · Attempt 与 Invocation 是两个身份

身份范围何时存在
Attemptper-Ticket/per-Role（Merger 为 per-Batch）engine 决定派发时就有，此时还没有进程
Invocationrun 内全局唯一、单调只有 spawn 成功后才分配并公开 PID

所以 planned Attempt 在 Agent 尚未启动时就可查看，而不会拿一个不存在的进程冒充它。 被动 Recovery inventory、重复 probe、SSE 重连都不产生 Attempt。

4 · 共享 Merger 是 batch 级对象

一个 batch 只有一个逻辑 Merger Inspector，多个 Ticket lane 引用它；其内部按序列出每次真实 Attempt/Invocation（merge、close-only、重试）。逐票 Delivery 结果仍各自独立。

5 · 只读，且与控制能力彻底分离

  • 只绑定 127.0.0.1，端口由 OS 分配
  • 独立的 per-run read token，与 control token 无法互换
  • 没有 stop / retry / approve / resume 任何 mutation route
  • 响应 Cache-Control: no-store + Referrer-Policy: no-referrer，页面不加载任何外部资源
  • journal、token metadata、最终 HTML 均为 0600；read token 不进 events、Role 日志、access log 或导出

6 · 关页面不影响 run

companion supervisor 只在 HTTP worker 自身异常退出时重建；关页面与 SSE 断线不触发重建，也不影响采集。 run 终态后冻结 history、导出自包含 dashboard.html，server 保留 24 小时，静态文件长期可直接打开。

专家要确认的 unknowns

下面是实现时真正踩到或权衡过的地方，以及处置方式。

A · 我们放弃了「无法证明旧进程消失就不接管」

这是本次唯一的破坏性行为变更。原策略偏保守：writer socket 响应无法确认归属、历史 role-start 缺 PID、历史 PID 返回 EPERM 时都可能永久阻止接管。代价是用户调用 skill 后 可能长期不开工。

改为 liveness-first：只有 ownership channel 能连上并正向证明同一 worktree 的 AFK writer 仍在运行时， 才让该 Ticket 进入 waiting-writer；否则默认没有 Role 在跑，恢复现场并开工。

被接受的取舍：旧 daemon 已消失、但它派生的、已脱离 ownership channel 的子进程仍可能存在的 理论风险。仍然有效的不变量：active recovery guard 继续串行化恢复；多 worktree、错误仓库绑定、 locked/prunable、Git conflict 等非 writer blocker 语义不变——本决策不授权通过猜测或丢弃现场来绕过它们。

已写入 ADR 0007，并有专门测试锁住（stale socket、未知响应、历史 PID 三类都不再阻塞）。

B · 完整性失败时明确认错，而不是假装完整

journal 写入失败后 run 继续，但公开 status 与页面必须显示 degraded/incomplete 并给出缺口原因。 我们选择让系统承认记录不完整，而不是在没有证据时继续宣称完整。

C · 不归档「hidden reasoning」

只展示 provider/CLI 实际发出的内容。不推断、不合成未公开的 chain-of-thought。同理，stdout/stderr 的顺序 是 observer 收到时的顺序——界面不声称能恢复 OS 层未被观察到的更精细先后关系。

D · 不提供 Raw 标签页，但也不简化 payload

transport envelope 可以被排版，payload 内容与顺序不得被简化、截断、改写或脱敏。未知 provider 事件 走通用结构化渲染，不能静默丢弃字段。

E · 测试只走公开 CLI 黑盒 seam

不 import engine、process supervisor、provider parser 或 Dashboard 私有对象。clock、worker crash、 磁盘与导出故障都通过公开 start 的受控 PATH/env adapter 注入。这样测试锁的是外部行为， 不是模块拆分——重构不会无谓地弄红它们。

明确的非目标

  • 不做多 run 聚合、历史中心或跨项目总览
  • 不绑定非 localhost 地址，不做远程访问或团队共享
  • Dashboard 内不提供任何控制能力
  • 不为上线前的旧 daemon 热注入采集
  • 不恢复旧 Agent session、旧 daemon 内存、旧 Attempt 或旧 Reviewer verdict
  • 不把原型的视觉风格定为正式 design system（颜色、边框、pill 密度、字体明确不在验收范围）
  • 自动删除旧 branch / worktree / dirty files / commits / 日志

移动端不在范围内。页面只在桌面使用，验收只在 1440 视口做。窄屏堆叠样式保留但不作为验收条件。

已知缺口 如实列出

  • 未在真实 provider 上端到端跑过。全部验证使用受控 fake provider。真实 Claude/Codex/Pi 的 transport 字段差异尚未实测——adapter 把它们限制在 observation 层，但这是未验证的假设。
  • 多 run 并发未覆盖。当前每个 run 一个 companion；两个 run 同时开 Dashboard 的行为没有测试。
  • 慢客户端只在有界缓冲层面验证。确认不阻塞采集，但没有压测极端并发连接数。
  • 代码质量问题未清理。审查发现 scope 字段组在多处重复、测试 fixture 与 recovery 套件有重复， 属于重构范畴，未纳入本次改动。

建议的下一步

  1. 在一个真实仓库用真实 provider 跑一次，确认 transport 适配无意外。
  2. 汇入你日常用的那个项目，实际用一两天——重点看四层状态在真实失败场景下是否仍然清晰可判。
  3. 再讨论视觉收敛（当前明确不是产品 design system）。
