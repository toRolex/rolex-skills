# AFK Reviewer 回到复核者定位，只有终局信号能决定失败

Issue #12 的决策，一次纠正三处同族缺陷：**过程信号（单次工具失败、`permission_denials` 数组、中途 stderr）不再有否决权；只有终局信号（`is_error` / `subtype` / 退出码 / 有无合法结构化封套）能决定失败。** 具体是三条相互支撑的改动：Reviewer 的验收标准对齐上游 sandcastle、权限判定改由终局仲裁、停滞检测只统计引擎自己的业务判断。

## 为什么原策略必须改

两类本不该发生的失败，都源于同一个错误——把过程信号当成终局判决。

**成功的 Reviewer 被判失败。** Reviewer 完成审查、自报 `passed`、输出合法封套与完成信号，只是因为过程中**试过一次**被本机 hook 拦截的工具调用（随后自己改道完成了任务），就被判「权限拒绝」，整票阻塞。上一轮 run 里 reviewer #7 与 #22 都是这样被误杀的，同一票同一轮的 Implementer 反而正常通过。判定依据是 `result` 事件中 `permission_denials` 非空——它被当成了独立判决，而不是终局错误的辅助证据。

**瞬时故障被放大成永久停滞。** 载体层的一次瞬时失败（如 API 返回 `500 EOF`），或上面那种误判，只要**连续三轮原因字符串相同**，该票就被永久置为「等待用户」，不再重试。引擎无法区分「这项工作在当前规格下真的做不成」与「刚才网络抖了一下」，使用者只能逐个翻日志判断某票是真失败还是被误杀。

同时，Reviewer 被本机改造成了「验收关卡」（要求提交测试清单、未执行项 `not-run` 即 blocked、条件必填 `acceptanceResolution`），却没有同步降低它的失败成本——判失败即阻塞整票交付。上游把 Reviewer 定位为「复核并直接改进」，两者已经脱节。

## 决策

**Reviewer 验收对齐上游**

- 移除 Reviewer 专属的 `not-run` 硬阻断与「tests 中存在 failed 即拒绝」判定；tests 对 Reviewer 变为**信息性**。`acceptanceResolution` 连同它在 prompt 中的要求、引擎在「前序存在 failed/not-run」时的强制校验一起删除。
- 保留 Git 层的交付核实（分支有提交、有变更、无未提交的已跟踪改动、无进行中的 merge/rebase）。这是基于 Git 事实的判据，不是角色自报，上游同样要求 Reviewer 在分支上直接改动并提交。
- 保留结构化结果封套。上游不需要它是因为上游编排器只看退出码；本引擎需要它来协调逐票状态、关闭 Issue 与 Merger 交接。**tests 字段保留但可为零/空**，不再构成 Reviewer 的门控。
- Reviewer prompt 的执行段按其上游原版重写：直接改、跑测试确认没弄坏、有改进就提交、本来就干净就不动。

**权限判定：终局信号是权威**

- Claude `result` 事件中 `permission_denials` 非空不再单独构成权限拒绝；仅当同一终局为失败（`is_error: true`、`subtype` 以 `error` 开头，或无有效结果）时才结合 denials 判定。
- 成功终局（有结果文本、无终局错误）**清除**过程中累积的权限拒绝标志，覆盖 claude/codex/pi 三种 provider；stderr 累积的拒绝判定同样受终局洗白，invokeAgent 后来行若出现 terminal 失败会把已累积的成功清掉。宽泛的鉴权错误正则只在终局/终止性错误文本上生效。
- 保留：终局层面的显式权限拒绝事件、取消、取消来源未知仍判阻断并等待用户——这些都是终局信号，不是过程噪音。中途显式拒绝 + 成功终局照样被洗白，只有终局层面显式才阻断。

**停滞检测：只统计引擎的业务判断**

- 判据是角色结果**是否带有合法结构化封套**。带封套说明引擎走到了自己的判断（例如「自报通过但无可交付提交」），计入停滞；不带封套说明是载体/Provider 层失败（进程崩溃、鉴权、瞬时 API 错误），只发布观测（`stagnationCounted: false`），由既有重试继续，不计入停滞。
- 保留同因连续拒绝达阈值后转入「等待用户」的终局，以及「任何新的 Gate 接受都会清零计数」的既有行为。
- 停滞原因的文案必须让使用者区分「业务死结」与「载体故障」。

**不变的部分**

- Merger 的验证要求（合并后跑实际检查、summary 前置条件）不变；Implementer「必须产出提交」不变；角色选择（逐角色 harness/模型/effort）与 Dashboard 观测不变。

## 被接受的取舍

- **净效果是削弱一层保护**：Reviewer 不再独立门控测试。依据是上游把它定位为「复核并直接改进」而非验收关卡，而本机此前只提高了它的严格度、没有同步降低它的失败成本。若日后需要恢复测试门控，应作为独立决策提出，并同时重新设计失败成本。
- **成功终局会清掉过程性的拒绝记录**，因此一次"真实的权限拒绝"若发生在成功终局之前也会被忽略。这与本引擎的失败成本对称性一致（判失败即阻塞整票），也与 `providers.mjs` 里既有的「允许后续成功终局恢复、不依赖历史回退」设计意图一致——恢复机制本已实现，此前唯独把权限拒绝排除在外，本决策是补上遗漏而不是新增机制。
- **宽泛鉴权正则收窄到终局文本后**，中途出现的 `unauthorized` 字样不再翻转判定；若认证真的失效，终局仍会报错并阻断。
- 不停留在「过程信号更可信」的直觉上：一次被拦截的工具调用与一次成功的终局相比，后者才是任务的真实结果。

## Consequences

- `afk-dashboard.test.mjs` 中原「Self-report passed 但必需验证 not-run → Gate rejected 与 Delivery blocked」用例改为断言**同一场景下引擎独立接受并发布 Gate accepted**，且不得为该 Attempt 发布 gate-rejected。
- `afk-recovery.test.mjs` 新增两条锁：权限误判回归（假角色先产出被拦截的工具结果、随后成功终局且仍带非空 `permission_denials` → 该票不 blocked、run 继续推进）；载体层失败不计入停滞（假角色连续多轮返回无封套的失败 → 重试不被 3 轮阈值封顶、run 不转入 waiting-user）。
- 既有 `gate-stagnation` 用例保留并强化：带合法封套的业务拒绝必须发布 `stagnationCounted: true` 的 Gate rejected 并转入等待用户，防烧钱保护未被削弱。
- 停滞文案带上「引擎业务判断连续失败」的判别词，使用者可直接区分该改规格还是该重试。
