# Logic Prototype（逻辑原型）

一个单一的、自包含的 HTML 文件（一个**可分享的演示**），让任何人都能通过点击按钮驱动 state model。当问题是关于**业务 logic、state 转换或数据形状**时使用：那种在纸上看起来合理、只有推进真实用例时才感觉不对劲的东西。

因为它是单文件、无需安装，你可以把它交给一个非开发者（设计师、PM、领域专家），让他们自己感受这个模型。所以它说他们的语言，而不是代码的语言。

## 什么时候这是正确的形状

- "我不确定这个 state machine 是否处理了 X 然后 Y 的 edge case。"
- "这个数据模型真的能让我表示……这种情况吗？"
- "在写之前，我想摸清 API 应该长什么样。"
- 任何有人想**按按钮并观察 state 变化**的情况。

如果问题是"这应该长什么样"，branch 就选错了。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，写下你在 prototype 化的 state model 和问题。一段话，放在演示的顶部（可见的简介里，不只是注释）。回答了错误问题的 logic prototype 是纯粹的浪费，所以把问题写清楚，这样以后可以检查，无论用户现在是看着还是 AFK 之后再回来。

### 2. 把 logic 隔离在一个可移植的 module 里

把真正的 logic（回答问题的那部分）放在一个 `<script>` 块里，写成一个小而纯净的 module，以后可以提取出来直接放进真实代码库。它周围的页面是一次性的；这个 module 不是。

正确的形状取决于问题：

- **纯 reducer**：`(state, action) => state`。当 action 是离散事件、state 是单个值时很好。
- **state machine**：显式的 state 和转换。当"现在到底哪些 action 是合法的"本身是问题的一部分时很好。
- **一组小纯函数** 作用于一个普通数据类型。当没有隐式的当前 state、只是变换时很好。
- **带清晰方法面的类或 module**，当 logic 真正拥有持续的内部 state 时。

选择最适合所问问题的形状，*而不是*最方便接到页面上的那个。保持纯净：没有 DOM、没有 `document`、没有伸进它内部的按钮处理。页面调用它；没有任何东西反向流动。这就是让 prototype 在其生命周期之外仍然有用的原因：一旦问题得到回答，验证过的 reducer / 机器 / 函数集就能自己提进真实 module。

### 3. 构建可分享的 HTML 文件

单文件，纯 HTML/CSS/JS：没有框架、没有打包器、没有服务器，一切都内联，所以双击就能打开，被邮件转发也能活。任何人都应该能通过打开它来运行。

为非开发者而写。每个标签都用**领域语言**，而不是代码：按钮和 state 读起来像业务，而不是 reducer。用浅白的话解释正在发生什么。

用干净的分层布局，从上到下：

1. **标题和一行解释**：这个演示让你探索什么（第 1 步的问题）。
2. **当前 state**：全部相关 state，渲染成可读的面板（有标签的字段，不是裸的 JSON dump），每次点击后重新渲染，让变化可见。在有助于非开发者跟随的地方，指出刚刚改变了什么。
3. **自由玩耍按钮**：每个 action 一个按钮，始终可用，让任何人能以任意顺序戳模型。每次点击分发它的 action 并重新渲染 state。
4. **引导式 walkthrough**：一组**scenarios**，每个标签页一个。每个标签页包含 scenario 的简短浅白描述（它搭建的情况和要注意什么），以及下面该 scenario 的按顺序要**按的按钮**。每一步都是真实按钮：点击执行那个 action 并进入下一步。开始 walkthrough 会重置到已知初始 state，让 scenario 每次都同样运行。

选择展示棘手用例的 scenarios，那些在纸上难以推理的情况：快乐路径、一个棘手的 edge case、一次本应非法的事件的尝试。

保持美观但有节制：干净的排版、充足的字距、一个强调色。没有动画、没有噱头：没有与 state 和按钮竞争的东西。

### 4. 交给对方

把文件发给他们，或替他们打开。他们会在方便的时候点击 walkthrough 和自由玩耍；有趣的时刻是他们说"等等，那不应该可能"或"嗯，我以为 X 会不同"；那些是_想法_里的 bug，这才是重点。如果他们想要新 action 或新 scenario，加上它们。prototype 会演化。

### 5. 捕获答案和 prototype

一旦 prototype 回答了问题，捕获答案，然后按 [SKILL](SKILL.md) 描述的方式捕获 prototype。logic 特定的映射：验证过的 reducer / state machine / 函数集提进真实 module（决策，被吸收）；HTML 外壳跟着去那个把 prototype 保持为一手来源的一次性 branch，而且作为单文件，它在那边保持零门槛可重跑。

## Anti-patterns

- **不要加测试。** 需要测试的 prototype 不再是 prototype。
- **不要接到真实数据库。** 使用内存 state，除非问题专门关于 persistence。
- **不要泛化。** 没有"如果我们以后想支持 X 呢。"prototype 回答一个问题。
- **不要把 logic 和页面搅在一起。** 如果纯 module 引用了 DOM、`document` 或按钮处理，它就不再可提取。保持页面作为纯 module 上的薄壳。
- **不要伸手去拿框架、打包器或服务器。** 接收者双击打开的单文件；React app 或 dev server 击败了"可分享"。
- **不要把 HTML 外壳发到生产环境。** 页面是为被人亲手点击而优化的。它背后的 logic module 才是值得保留的部分。
