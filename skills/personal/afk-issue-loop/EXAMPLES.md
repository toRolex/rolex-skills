# AFK Issue Loop 示例

## 当前 agent 直接开工

用户：`/afk-issue-loop 3 4 5 6`。四票资格与依赖满足，现场可用。

你读取已有任务，建各自的 worktree，直接派四个 Implementer。某票完成并退出就派该票 Reviewer，其他票仍可实现。首批结果明确后只派一个 Merger，处理通过审查的成功集。

不先把这条调用转发给“总调度者”，也不以准备子任务、调度脚本或计划文件已经完成来报告开工。宿主要求的调用脚本可以承载上述业务步骤，但不增加角色层级。

## A→C，B 独立

1. 本批固定 A、B，两个 Implementer 并发；C 等待 A。
2. A 完成后立即独立审查，B 继续实现。A 审查通过仍等批末，不先合并或补入 C。
3. B 审查结束后，Merger 顺序合 A、B。核对交付与关闭后刷新依赖，下一批才派 C。
4. A 已交付、关闭，仅 worktree 清理失败：记录待清理，不重做 A。只有现场安全时才继续。

五票独立就绪时本批最多四票，空出的本批位置不补第五票；只有一票就绪时直接启动，不等凑满。

## 父 SPEC 不是执行依赖

用户说“#1 是 SPEC，其他是 Tickets”。正文有 `Parent #1`，原生 parent 查询明确无父节点，但原生 blocked-by 完整且无阻塞。

读取 #1 作为上下文，排除其实现，直接处理就绪 Tickets。不要求用户先建立原生父子关系；若正文另有明确 `Blocked by #2` 且与原生依赖矛盾，才阻塞相关票并说明问题。

## 只读请求出现 EOF

读取 #14 的 blocked-by 返回 `unexpected EOF`。用原方式最多再试两次；成功后继续选票，不重建调度，也不要求用户输入“原协议重启”。

仍失败则记录 #14 依赖未知，#14 及其依赖者暂不启动；已完整核对的独立票继续。不能把 EOF 当成没有依赖，也不能把未开工的票登记成实现失败。

## 用户要求重新开始

旧记录提到已被用户停止的调度者和四个 worktree。你只核对本次要用的现场有没有写者、已有成果能否使用；开新运行，直接派本批 Implementer。没有恢复旧调度者这一步。

旧 worktree dirty、原始基线缺失或退出不明时保留它，报告受影响票。无关历史不必清空；用户停止也不能靠换一个代理绕过。

## 结果只在结束时返回

Merger 能合并和验证，但不能持久保存报告，也没有中途回复通道。它处理本批可处理项后返回逐票结果，由你保存、核对，再关闭已交付的 Issues。无需第二个 Merger；清理前将唯一证据留在待删 worktree 之外。

实现者报告“功能已经存在”，但相对原始基线无变化：核实为历史已交付就只收尾，否则记无交付变化并跳过，不因返回成功白跑审查和合并。Reviewer 无新增提交则不同，已有实现仍可通过独立审查。

用户明确本 Ticket 免测时，记录未执行，其余验收照常；一次实际测试失败不能改称免测。

## 部分失败

A 实现失败、B 审查通过：A 本次跳过，批末只合 B；A 的下游等待，下一批可处理独立票。全批失败则不派 Merger。Reviewer 没有新增 commit 但独立审查和测试通过，仍算成功。

合并 A 成功，B 合入后测试失败，C 未处理：保留 A 的交付事实，B/C 本次跳过，目标存在未验收内容，停止后续合并。A 关闭或清理失败只登记待收尾，不重新实现 A。

退出不明时失败归类不释放现场；有限观察后仍不能证明隔离，就保留成果并报告阻塞。状态查询或通知已能证明相关写者退出时，直接正常交接，无需另跑退出探测。
